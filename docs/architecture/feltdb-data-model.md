# FeltDB Data Model: Proposed Schema and Collection Design

**Status**: Architecture Planning (No Implementation)  
**Scope**: Concrete FeltDB collections, relationships, lifecycle, and durability semantics

---

## 1. Overview

This document specifies the proposed FeltDB schema for felt-session. It maps the inventory from the assessment onto concrete collections, with explicit semantics for durability, recovery, and lifecycle.

**Core principle**: FeltDB owns durable application state and event history. Filesystem remains the source of truth for git worktrees and large artifacts.

**Architecture**:
- **Event history** (append-only): `session_events` collection
- **Materialized state** (mutable, versioned): `sessions`, `executions`, `timers`, `workspaces`, `automations`
- **Index/cache** (derivable): None required; queries suffice
- **External references** (pointers): Artifact paths, worktree locations, provider URLs

## 2. Core Collections

### 2.1 Collection: `sessions`

**Purpose**: Materialized session metadata and lifecycle state

**Primary identity**: `id` (session_id: string, format: "os-{uuidv7}")

**Fields**:
```typescript
{
  id: string;                           // Primary key: "os-0191jq2v0000"
  created_at: ISO8601;                  // Immutable: session creation time
  updated_at: ISO8601;                  // Mutable: last activity timestamp
  
  // Workspace/project identity
  workspace_id: string;                 // Foreign key → workspaces.id
  repository_url: string;               // Git remote URL (immutable)
  repository_branch: string;            // Target branch (may change)
  
  // Session state machine
  status: enum;                         // Values: Creating | Ready | Running | Paused | Stopped | Archived
  status_reason?: string;               // Optional: reason for status (e.g., "User paused", "Error: timeout")
  
  // Resumability markers
  generation: uint64;                   // Monotonic counter, incremented on pause/resume
  current_run_id?: string;              // Foreign key → executions.id (nullable, current execution)
  current_turn_index: uint64;           // Latest turn number (0-indexed)
  
  // Metadata
  metadata: {
    title?: string;
    description?: string;
    labels?: string[];
    tags?: Record<string, string>;
  };
  
  // Counters (derived, updated by events)
  event_count: uint64;                  // Total events in transcript (for UI)
  execution_count: uint64;              // Total executions (for UI)
}
```

**Indexes**:
- Primary: `id`
- Query: `workspace_id` + `status` (sessions by workspace and status)
- Query: `created_at` DESC (list sessions, recent first)
- Query: `updated_at` DESC (active sessions)

**Relationships**:
- → `workspaces.id` (workspace)
- → `session_events.session_id` (event history)
- → `executions.session_id` (execution history)
- → `timers.session_id` (active timers)

**Append/Update Semantics**:
- Created once at session creation
- Updated on status changes, turn completion, generation increment
- Status transitions only: Creating → Ready → (Running ↔ Paused)* → Stopped → Archived
- Generation increment: on pause/resume cycle

**Retention**:
- Lifetime: Until explicitly deleted/archived
- Cascade: Deleting session deletes session_events, executions, timers (foreign key cascade)
- Archive: Set status=Archived, retain all data

**Recovery Semantics**:
- On startup, query for sessions with status=Running or status=Paused
- For each, load latest execution and check if generation counter matches
- If not, session was interrupted mid-turn (see recovery plan)

### 2.2 Collection: `session_events` (Canonical Event History)

**Purpose**: Append-only, immutable event log for every session

**Primary identity**: `id` (UUIDv7, auto-generated by FeltDB)

**Fields**:
```typescript
{
  id: string;                           // Primary key: UUIDv7 (auto-assigned)
  session_id: string;                   // Foreign key → sessions.id (immutable)
  
  // Ordering and identity
  sequence: uint64;                     // Monotonic sequence within session (append-only)
  timestamp: ISO8601;                   // Event timestamp (typically slightly after creation)
  
  // Event classification
  event_type: enum;                     // Values: see section 2.2.1 below
  causality_id?: string;                // Correlation ID (links to turn/execution)
  source: enum;                         // Values: client | agent | automation | recovery
  
  // Event payload (event-specific)
  payload: Record<string, any>;         // JSON, structure depends on event_type
  
  // Sizing and reference handling
  content_size: uint32;                 // Bytes in payload JSON
  content_oversized: boolean;           // If true, see oversized_content_ref
  oversized_content_ref?: string;       // Path/URI to external blob store (if >1MB)
  
  // Metadata
  metadata: {
    source_client?: string;             // Client ID if from client
    user?: string;                      // User ID who triggered event
  };
}
```

**Indexes**:
- Primary: `id`
- Query: `(session_id, sequence)` compound unique (enforce append-only)
- Query: `session_id, timestamp` (range scan for events after time T)
- Query: `causality_id` (lookup events from single turn/execution)

**Event Types** (section 2.2.1):

| Event Type | Payload Fields | Source | Append To | Notes |
|---|---|---|---|---|
| `SessionCreated` | workspace_id, repository_url, branch | agent | session_events | Session init |
| `UserMessage` | content, format (markdown/code) | client | session_events | User input |
| `ModelCall` | model, temperature, max_tokens, prompt_tokens | agent | session_events | LLM invocation |
| `ModelChunk` | chunk (string, partial response) | agent | session_events | Streaming content |
| `ModelComplete` | response_tokens, finish_reason | agent | session_events | LLM result |
| `ToolCall` | tool_name, tool_input, tool_id | agent | session_events | Tool invocation |
| `ToolResult` | tool_id, result (JSON), duration_ms | agent | session_events | Tool completion |
| `ToolError` | tool_id, error_code, error_message | agent | session_events | Tool failure |
| `FileChange` | file_path, change_type (create/modify/delete), diff (optional) | agent | session_events | Git change |
| `FileCommit` | commit_hash, commit_message, files_changed | agent | session_events | Git commit |
| `TurnComplete` | turn_index, duration_ms, token_usage | agent | session_events | Turn finished |
| `CheckpointCreate` | checkpoint_id, checkpoint_name, metadata | agent | session_events | Checkpoint saved |
| `SessionPaused` | reason (optional) | client \| agent | session_events | Session paused |
| `SessionResumed` | resume_reason (optional) | client | session_events | Session resumed |
| `SessionArchived` | archive_reason (optional) | client | session_events | Session archived |
| `RecoveryDetected` | recovery_type, recovered_state | recovery | session_events | Crash recovery |

**Append/Update Semantics**:
- Immutable after write: no updates, only inserts
- Sequence generated by FeltDB (append-only counter per session_id)
- Insert failures are fatal (no retries, no duplicates)
- Import-first gate: session_events only written after turn execution completes

**Retention**:
- Lifetime: Same as session (cascade delete)
- Archival: Retain even after session archived (transcript immutable)
- No rotation/pruning (sessions are typically <1MB transcript)

**Recovery Semantics**:
- On resume, replay events from sequence N onward (where N is last processed turn)
- Idempotency: Sequence number prevents duplicate events
- Causality: causality_id links related events (tool_call → tool_result)
- Reconstruction: Process event stream in order to restore session state

### 2.3 Collection: `executions`

**Purpose**: Mutable execution state for agent operations (turns, tool calls, automations)

**Primary identity**: `id` (execution_id: UUIDv7)

**Fields**:
```typescript
{
  id: string;                           // Primary key: UUIDv7
  session_id: string;                   // Foreign key → sessions.id
  
  // Execution identity and type
  execution_type: enum;                 // Values: Turn | ToolCall | FileChange | Checkpoint | Automation
  execution_role?: string;              // Optional: agent role for Turn (e.g., "coder", "reviewer")
  
  // State machine
  status: enum;                         // Values: Pending | Running | Completed | Failed | Recoverable
  
  // Ordering and attempt tracking
  created_at: ISO8601;                  // Immutable: execution creation
  started_at?: ISO8601;                 // Mutable: when execution began
  completed_at?: ISO8601;               // Mutable: when execution finished
  attempt_count: uint32;                // Retry counter (0-indexed)
  
  // Execution data (input and output)
  input: Record<string, any>;           // Execution input (prompt, tool args, etc.)
  result?: Record<string, any>;         // Execution output (nullable until completion)
  error?: {
    code: string;
    message: string;
    recoverable: boolean;               // Can retry, or fatal?
  };
  
  // Durability markers
  idempotency_key?: string;             // Deterministic ID for deduplication (MD5 of input)
  replay_safe: boolean;                 // Can be safely retried without side effects
  
  // Metadata
  metadata: {
    turn_index?: uint64;                // For Turn executions
    model?: string;                     // For Turn executions
    tool_name?: string;                 // For ToolCall executions
    tool_id?: string;                   // Unique identifier for this tool call instance
    duration_ms?: uint32;               // Execution duration
    token_usage?: { input: uint32, output: uint32 }; // LLM token counts
  };
}
```

**Indexes**:
- Primary: `id`
- Query: `(session_id, created_at)` (executions for session, ordered by time)
- Query: `(session_id, status)` (unfinished executions, for recovery)
- Query: `status` (query by global status for maintenance)
- Query: `idempotency_key` (deduplication lookup, if populated)

**Relationships**:
- → `sessions.id` (parent session)
- ← Session.current_run_id (current execution reference)
- → `session_events.causality_id` (corresponding events)

**Append/Update Semantics**:
- Created: When execution starts
- Updated: Transition state → Running → Completed/Failed
- Idempotency: If idempotency_key present, retry uses same id and updates result
- Failure handling: Set status=Recoverable or status=Failed (fatal) based on error.recoverable

**Retention**:
- Lifetime: Same as session
- Cascade: Deleting session deletes all executions

**Recovery Semantics**:
- Query `status=Recoverable and created_at > last_boot` on startup
- For each recoverable execution, re-attempt using same execution ID and idempotency_key
- If retry succeeds, update result and set status=Completed
- If retry fails again and not recoverable, escalate to human operator

### 2.4 Collection: `timers` (Durable Timer Registry)

**Purpose**: Persist timer state across restarts (used for exponential backoff, delayed retries)

**Primary identity**: Composite key: `(session_id, kind, due_at)` or generate single `id: UUIDv7`

**Fields**:
```typescript
{
  id: string;                           // Primary key: UUIDv7
  session_id: string;                   // Foreign key → sessions.id
  
  // Timer identity
  kind: enum;                           // Values: Retry | Callback | Heartbeat | Custom
  
  // Scheduling
  due_at: ISO8601;                      // When timer should fire
  created_at: ISO8601;                  // Immutable: when timer was created
  
  // Retry semantics
  attempt_count: uint32;                // How many times executed (0 = not yet fired)
  max_attempts?: uint32;                // Optional: max retry attempts (null = unlimited)
  backoff_strategy: enum;               // Values: Exponential | Linear | Fixed
  backoff_base_ms: uint32;              // Base delay in milliseconds
  
  // Correlation
  correlation_id?: string;              // Foreign key → execution, automation, or other
  metadata: Record<string, any>;        // Timer-specific data
  
  // Status
  active: boolean;                      // Can this timer fire, or has it been cancelled?
}
```

**Indexes**:
- Primary: `id`
- Query: `due_at` ASC (find timers that should fire now)
- Query: `session_id, active` (timers for recovery)
- Query: `correlation_id` (find timer for specific execution)

**Relationships**:
- → `sessions.id` (parent session)
- → `executions.id` (optional: timer for specific execution)

**Append/Update Semantics**:
- Created: When timer is registered
- Updated: On fire (attempt_count++, due_at recalculated)
- Deleted: When timer completed or cancelled (active=false)

**Retention**:
- Lifetime: Until fired or cancelled (soft delete via active=false)

**Recovery Semantics**:
- On startup, query `due_at <= now and active=true`
- For each timer, re-fire or update due_at if backoff not yet expired
- Prevent stale timers: If created_at + max_ttl < now and still active, mark recoverable error

### 2.5 Collection: `workspaces`

**Purpose**: Durable workspace/project metadata (shared across sessions)

**Primary identity**: `id` (workspace_id: UUID)

**Fields**:
```typescript
{
  id: string;                           // Primary key: UUID
  
  // Identity
  name: string;                         // Human-readable workspace name
  slug?: string;                        // URL-safe identifier (unique)
  
  // Configuration
  base_path: string;                    // Filesystem path for git worktrees
  
  // Metadata
  config: {
    default_branch?: string;
    default_model?: string;
    sandbox_kind?: string;              // Kind of sandbox to use
    mcp_scope?: string;                 // MCP allowed tools/integrations
  };
  
  // Timestamps
  created_at: ISO8601;                  // Immutable
  updated_at: ISO8601;                  // Mutable
}
```

**Indexes**:
- Primary: `id`
- Query: `slug` unique (lookup by slug)
- Query: `created_at` (list workspaces)

**Relationships**:
- ← `sessions.workspace_id` (sessions in this workspace)

**Retention**:
- Lifetime: Until explicitly deleted
- Cascade: Deleting workspace should delete/archive all sessions (or reject if sessions exist)

### 2.6 Collection: `automations`

**Purpose**: Durable automation definitions and state (shared, infrequently changing)

**Primary identity**: `id` (automation_id: UUID)

**Fields**:
```typescript
{
  id: string;                           // Primary key: UUID
  
  // Identity
  name: string;
  description?: string;
  
  // Trigger and actions
  trigger: {
    kind: enum;                         // Values: OnSessionEvent | OnTimer | OnWebhook
    filter?: Record<string, any>;       // Trigger-specific filter (e.g., event_type=ModelComplete)
  };
  
  actions: Array<{
    kind: string;                       // Action type (e.g., "CreateSession", "SendNotification")
    config: Record<string, any>;        // Action-specific config
  }>;
  
  // State
  enabled: boolean;
  
  // Scheduling
  runs: Array<{
    execution_id: string;               // Foreign key → executions.id
    triggered_at: ISO8601;
    status: enum;                       // Running | Completed | Failed
  }>;
  
  // Timestamps
  created_at: ISO8601;
  updated_at: ISO8601;
}
```

**Indexes**:
- Primary: `id`
- Query: `enabled` (active automations)
- Query: `trigger.kind` (trigger-type lookups)

**Retention**:
- Lifetime: Until deleted
- Archive: Set enabled=false (retain definition and run history)

## 4. Large Object Handling Strategy

### Problem
Event payloads can be large:
- Tool results: 10-100KB+ (LLM context, API responses)
- File changes: 1-10MB (large diffs)
- Model responses: 10-100KB (long outputs)

Embedding all in FeltDB would:
- Bloat collection indexes
- Slow down event queries
- Increase memory footprint

### Solution: Reference Pattern

**Strategy 1: Inline for small (<10KB)**
- Store directly in `session_events.payload` or `executions.result`
- Simpler, no external dependencies

**Strategy 2: External blob store for large (>10KB)**
- Store blob in filesystem or S3
- Reference in collection: `oversized_content_ref: "file:///session/{id}/tool-output-{uuid}.json"` or `s3://bucket/blob-{hash}.json`
- Mark: `content_oversized: true`
- On read, fetch from external store if needed

**Strategy 3: Truncate + Link for very large (>1MB)**
- Store first 10KB in `payload` (clamped content)
- Store full in external store with reference
- Mark: `content_clamped: true, content_size: 5000000, content_ref: "..."`
- UI shows clamped content + "see full" link
- Export/archive includes external reference

### Implementation
- Thresholds: TBD by performance testing
  - Inline: <10KB (default, most events)
  - External: 10KB-1MB (reference with download)
  - Clamped: >1MB (truncated + reference)
- External store: Filesystem (in session worktree) or S3 (if multi-machine)
- Reference format: URI scheme (file://, s3://, http://) for portability

## 5. Concurrency and Transaction Semantics

### 5.1 Transaction Boundaries

**Write operations**:
- `sessions.update_status()`: Single-record write transaction
- `session_events.append()`: Single record insert (append-only)
- `executions.create()`: Single record write
- `executions.transition()`: Single record update (state machine transition)

**Multi-record writes** (require ACID semantics):
- Turn completion:
  1. Append session_events entries (multiple)
  2. Transition execution to Completed
  3. Update sessions.current_turn_index and updated_at
  - **Atomicity required**: All or nothing
  - **Isolation**: Session-level (within session)
  - **Durability**: Written before acknowledgment to client

### 5.2 Conflict Resolution

**Read-Modify-Write** (for optimistic locking):
- All mutable collections support versioning (implicit via timestamps)
- Executions use generation counter for optimistic locking
- Sessions use generation counter for resumability

**Retry Policy**:
- Conflicts on execution state: Retry with exponential backoff (max 3 times)
- Conflicts on session update: Retry with CAS (compare-and-swap) on generation
- Timeout: 5s max per transaction

### 5.3 Concurrency Scenarios

| Scenario | Mechanism | Details |
|---|---|---|
| Multiple clients read session | Concurrent reads | No conflict (FeltDB handles) |
| Agent + client update session | Session-level serialization | Session.generation prevents double-start |
| Tool callback + turn end | Execution isolation | Each execution has own ID, no conflicts |
| Timer fires during turn | Lock-free | Timer is independent collection, separate transaction |
| Session resume while running | Generation mismatch | Detected by resumeInterruptedRuns(), marked Recoverable |

## 6. Query Patterns and Access Paths

### 6.1 Session Queries

```typescript
// List sessions in workspace
Query(sessions)
  .where("workspace_id", "=", workspace_id)
  .where("status", "!=", "Archived")
  .orderBy("updated_at", "DESC")
  .limit(100)

// Get session by ID
Query(sessions)
  .where("id", "=", session_id)

// Resume session (load state)
Query(sessions)
  .where("id", "=", session_id)
  .single()
→ result.current_run_id, result.generation

// Detect interrupted sessions
Query(sessions)
  .where("status", "IN", ["Running", "Paused"])
→ for each, check if generation matches last execution
```

### 6.2 Event Queries

```typescript
// Get events after sequence N (resume)
Query(session_events)
  .where("session_id", "=", session_id)
  .where("sequence", ">", last_processed_seq)
  .orderBy("sequence", "ASC")

// Get turn events (causality)
Query(session_events)
  .where("causality_id", "=", turn_id)
  .orderBy("sequence", "ASC")

// Get recent events (UI feed)
Query(session_events)
  .where("session_id", "=", session_id)
  .orderBy("sequence", "DESC")
  .limit(50)
```

### 6.3 Execution Queries

```typescript
// Get unfinished executions (recovery)
Query(executions)
  .where("session_id", "=", session_id)
  .where("status", "IN", ["Pending", "Running", "Recoverable"])

// Get execution by ID
Query(executions)
  .where("id", "=", execution_id)

// Get recoverable executions (global, for background recovery)
Query(executions)
  .where("status", "=", "Recoverable")
  .where("created_at", ">", boot_time - 1_hour)
  .orderBy("created_at", "ASC")
```

### 6.4 Timer Queries

```typescript
// Get timers to fire
Query(timers)
  .where("due_at", "<=", now)
  .where("active", "=", true)
  .orderBy("due_at", "ASC")

// Get timers for session (recovery)
Query(timers)
  .where("session_id", "=", session_id)
  .where("active", "=", true)
```

## 7. Durability Contracts

### 7.1 Write Durability Levels

**Level 1: In-Process**
- Write is acknowledged to caller
- NOT yet durable
- Risk: Process crash before flush

**Level 2: FeltDB Append**
- Written to FeltDB collection
- Durable on the local machine
- Risk: Machine crash (mitigated by OS fsync)

**Level 3: Sync-to-Disk**
- FeltDB fsync() completes
- Fully durable on local machine
- Used for: session_events (events), turn completion

**Level 4: Replicated** (future)
- If multi-machine support added
- Replicated to remote FeltDB
- Not in Phase 1

### 7.2 Durability Policy by Collection

| Collection | Durability Level | When Acked | Notes |
|---|---|---|---|
| sessions | Level 3 (fsync) | After status updated | Critical for resumability |
| session_events | Level 3 (fsync) | After event persisted | Critical for audit trail |
| executions | Level 2 (append) | After execution created | Updates can be Level 2 |
| timers | Level 2 (append) | After timer registered | Best-effort retry |
| workspaces | Level 2 (append) | After creation | Rarely changed |

### 7.3 Crash Recovery Guarantees

**Guarantee 1**: No lost events
- session_events written with Level 3 durability
- On restart, replay from last processed sequence number
- Idempotent: re-adding same event is safe

**Guarantee 2**: No duplicate tool results
- Each execution has unique execution_id
- Idempotency key (if present) prevents duplicate processing
- If tool result received twice, second insert fails due to duplicate ID

**Guarantee 3**: Session state consistency
- sessions.generation counter prevents double-start
- On resume, generation must match execution generation
- If mismatch, session marked Recoverable

**Guarantee 4**: Ordered tool calls
- Tool calls within a turn are sequenced by session_events.sequence
- No race between tool 1 result and tool 2 invocation

## 8. Schema Version Strategy

### 8.1 Versioning

**Schema version**: Stored in FeltDB metadata (not per-document)

**Current**: v1.0

**Upgrade path**:
- Define migrations in code (not in FeltDB)
- On startup, detect schema version
- If outdated, run migrations (add fields, backfill defaults)
- Write new version number

### 8.2 Backward Compatibility

**Strategy**: Additive only (Phase 1)
- Add new fields with defaults
- Never remove fields
- Never change field types
- Version handling:
  - v0 (pre-FeltDB): Migrated via adapter pattern
  - v1 (initial): Current
  - v2 (future): Defined in next PR

## 9. Index Strategy and Query Performance

### 9.1 Indexes to Create

**Essential**:
- `sessions.id` (PK)
- `sessions(workspace_id, status)` (compound)
- `sessions(created_at DESC)` (list)
- `session_events(session_id, sequence)` (compound unique)
- `executions.id` (PK)
- `executions(session_id, status)` (compound)
- `timers(due_at ASC, active)` (compound)

**Nice-to-have** (optimize if queries slow):
- `session_events(causality_id)` (turn lookup)
- `executions(idempotency_key)` (deduplication)
- `workspaces.slug` (unique)

### 9.2 Query Performance Estimates

**Expected volume** (from assessment):
- 10-100 active sessions/day
- 50-100 events/session
- 1000 total sessions archived over time
- ~50K total events
- ~100K total executions
- ~500 active timers

**Performance expectations**:
- Session list: <100ms (with workspace_id + status index)
- Get session: <10ms (direct lookup)
- List events: <50ms (session_id + sequence)
- List unfinished executions: <100ms (session_id + status index)

**No optimization needed** if queries complete in <500ms (user-facing) or <10s (background).

## 10. Retention and Cleanup

### 10.1 Retention Policies

**Never delete**:
- session_events (append-only history, never modify or delete)
- Completed executions (audit trail)

**Archive (soft delete)**:
- Sessions: Set status=Archived, retain all related events/executions
- Automations: Set enabled=false

**May delete**:
- Timers: After firing or cancellation (hard delete ok)
- Recovery-marked executions: After 7 days if still failed (operator decision)

### 10.2 Cleanup Operations

**Startup cleanup**:
- Query `executions` with status=Recoverable and created_at < boot_time - 1_day
- Mark as failed (recovery failed, human intervention needed)

**Periodic maintenance** (every 24h):
- Query `timers` with active=false and created_at < 7_days_ago
- Archive/delete old inactive timers

**No automatic archive**:
- Sessions NOT automatically archived by age
- Operator must explicitly archive if space is a concern

## 11. Relationship Diagram

```
workspaces
    ↑
    │ workspace_id
    │
sessions
    ├─ id (PK)
    ├─ workspace_id (FK)
    ├─ status
    ├─ generation
    └─ current_run_id (FK to executions)

session_events
    ├─ id (PK)
    ├─ session_id (FK → sessions)
    ├─ sequence (append-only)
    ├─ event_type
    ├─ causality_id (→ executions or turn_id)
    └─ payload

executions
    ├─ id (PK)
    ├─ session_id (FK → sessions)
    ├─ execution_type
    ├─ status
    ├─ idempotency_key (deduplication)
    └─ ← sessions.current_run_id

timers
    ├─ id (PK)
    ├─ session_id (FK → sessions)
    ├─ due_at
    ├─ correlation_id (FK to executions, optional)
    └─ active

automations
    ├─ id (PK)
    ├─ trigger
    └─ actions
        └─ (references executions via runs array)
```
